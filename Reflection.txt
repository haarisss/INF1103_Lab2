Self-Reflection: Saving the Final Inventory Count

This hits Docker's ephemeral filesystem — containers don't have persistent storage by default.

I actually saw the contrast between Part 3 and Part 6 of this lab. In Part 3, I used a volume mount (-v "${PWD}:/usr/src/app"), linking my local folder into the container. In Part 6, I ran my custom image (docker run --rm -it inf1003-labs-smart-auditor) with no mount — auditor.py was baked in via COPY instead. Since I also used --rm, Docker deletes the entire container (and anything written inside it) the moment it stops.

So if my script wrote the final inventory count to a file inside the container's own filesystem, that file would exist briefly and then vanish with the container — it would never reach my Mac.

The fix is the same idea from Part 3: a volume mount. Anything written to a mounted path is actually being written to my host machine, not just inside the container. The underlying limitation is that containers are meant to be temporary and disposable — persistent data has to live outside the container, via volume mounts or Docker volumes.

In short, Docker containers are disposable by design — great for keeping environments clean and consistent, but not for storing data long-term. If this were a real inventory system, I'd need to mount a volume (or use a Docker volume) so the final count actually persists on the host machine instead of disappearing with the container.



LAB 3:

Moving from the monolithic loop of Week 2 to a modular design in Week 3 made me realize how essential functions are for building scalable applications. 

By writing a dedicated calculate_tax function that simply returns a value rather than printing it, the calculation logic is completely isolated from the user interface.

If business needs shift tomorrow such as the store manager wanting to save tax records to an external file, log them to a database, or format them differently in our automated Docker environment then,

we only need to change the single line of code handling the output. 

The core calculate_tax logic remains completely untouched. 

This isolation (separation of concerns) prevents bugs, simplifies debugging, and ensures the code can grow smoothly when new features like custom discounts or advanced reporting are introduced in the future.


Lab 4:
Having calculate_tax return a value instead of printing it directly keeps the function reusable and flexible. If it printed the tax internally, that's the only thing it could ever do with that number — the moment the manager wants something different (like writing the tax to a file, adding it to a running total, or including it in inventory.txt), the function would need to be rewritten.

By returning the value instead, I get to decide outside the function what happens to it. In my code, calculate_tax(result) returns a number that I then use in a print() statement myself — but that same returned value could just as easily be written to a file, summed into a tax total, or passed into another function, without touching calculate_tax at all.

This connects directly to what I saw with save_inventory() this week: the moment I needed the manager's data to persist to a file instead of just appearing on screen, having functions that return values (rather than print them internally) meant I could plug that returned data into a completely different output (a file) with no changes to the original function. If calculate_tax printed internally, I'd have no way to also save it — printing and saving would conflict, since a function can typically only do one or the other cleanly.

Conclusion: Returning values keeps functions single-purpose and decoupled from how their output is eventually used — screen, file, or otherwise — which is exactly what "pure" functions and modular design are meant to achieve.
